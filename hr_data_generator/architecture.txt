HR DATA GENERATOR - ARCHITECTURE OVERVIEW

Purpose
-------
This project generates a realistic, configuration-driven HR data set in an
Azure SQL database. It supports a full historical simulation and weekly
incremental updates. The primary consumer is a web app (chosen over a
Power BI-first design for easier AI/LLM integration); the schema must remain
usable as a Power BI semantic model too, in case a Power BI dashboard is
still wanted alongside it. Both consumers read the same tables, so the data
model must not assume either one.

Simulation state
----------------
The in-memory state is a dictionary of pandas DataFrames plus a few non-table
keys. It is the contract between simulators and the store. Every non-table key
is classified in STATE_KEY_REGISTER (infrastructure/state/checkpoint.py):
persisted keys (location openings and capacity streaks, department relocations,
the recruitment pipeline's candidate profiles, pending vacancy requests) are
saved in the checkpoint; transient keys (per-week caches, the employment index,
role_allocations, _accepted_applications) are rebuilt. A key that is neither a
schema table nor registered makes the checkpoint fail. `simulation_state` in SQL
stores the checkpoint: the NEXT ISO year and week to simulate, the seed, a
config fingerprint and the persisted keys as JSON (current_year/current_week
remain the last simulated week). An incremental run without a checkpoint or
with a different seed stops; run a full run first. Every schema table declares a
write_mode; the incremental load keeps a normalized per-row digest baseline of
each table and a write only sends rows that are new or really changed (DECIMAL
compared at its scale). Tables are read in primary-key order and both modes
start the weekly loop from that canonical order. Incremental runs rebuild
fact_workforce_snapshot and fact_salary_benchmark only for month-ends from the
first day of the month of the first simulated week; only the snapshot table may
lose rows (delete_missing). HR_SIMULATION_AS_OF replaces "today" (never in the
future) for validation runs.

Core reporting model
--------------------
Dimensions include:

- dim_employee, dim_department, dim_role and dim_manager
- dim_hire_source, dim_education and dim_location
- dim_absence_type, dim_ploegendienst, dim_satisfaction_band and
  dim_engagement_band
- dim_satisfaction_driver, dim_performance_driver and dim_engagement_driver
- dim_salary_band, dim_salary_scale, dim_event_type and dim_reden_vertrek
- dim_incident_type

Facts include:

- fact_employment: employment-event history; promotions, transfers, salary
  reviews and exits create or complete employment records. It stores relevant
  experience at the event start; cross-domain transfers retain only the
  configured share, while renewals, location moves and exits roll all
  experience forward. Tenure in every simulator (attrition, absence, safety,
  performance, salary review) is continuous service from
  dim_employee.Aaneengesloten_Indienst_Datum, never the current row's
  Startdatum. Internal eligibility (promotion, transfer, internal mobility)
  uses the same qualification and relevant-experience policy as external
  hiring (role_eligibility.qualification_and_experience_reason and
  carried_experience); a promotion or transfer inside a department keeps the
  employee's shift.
- fact_workforce_snapshot: one active employee per month-end (a leaver is
  excluded from the month-end on or after the departure date, so
  headcount(start) + hires - leavers = headcount(end)). This is the
  primary source for workforce trends, salary, performance, satisfaction,
  engagement, current relevant experience, capacity and employee-month
  absence metrics.
- fact_absence: absence and leave episode events. It stores workday and hour
  values plus the employment, pay and satisfaction context at episode start.
  Episodes still running at a departure are cut on the departure date
  (departure_records.close_open_absence).
- fact_vacancy and fact_recruitment: vacancy lifecycle and all applications.
  The accepted application determines the hire source of a filled vacancy.
- fact_salary_benchmark: monthly role, scale and salary-step benchmarks.
  Salaris is always a full-time (1.0 FTE) amount, floored by an indexed legal
  minimum wage (salary_benchmark.legal_minimum_salary, indexed with the market
  growth rate, flat before base_date). The director roles sit in the
  open-ended Boven-CAO scale, so Schaal_Max_Salaris is NULL for them.
- fact_manager_assignment: effective-dated manager history used to build the
  monthly workforce context. Assignments are sticky week to week; only
  orphans, new hires, department movers and over-capacity overflow move.
- fact_performance_review: annual performance-review events with one dominant
  performance driver. Score = stable personal level + partly persistent
  yearly deviation, calibrated via the config "performance" section.
- fact_safety_incident: one row per workplace safety incident, with the role,
  department, location and shift at incident time. Incidents that cause real
  lost time also create the matching fact_absence episode (Bedrijfsongeval),
  which only the safety simulator creates (absence.excluded_from_random_draw
  keeps it out of the ordinary sickness draw). Ploegendienst roles now also
  exist in Techniek and Logistiek, with per-department shift mixes in
  ploegendienst_assignment.by_department; safety base rates are calibrated to
  safety.target_incident_rate_by_department (safety_calibration.py).
  There is no stored key between the two facts (see modeling principles).

Modeling principles
-------------------
- Facts are not directly related to one another, in the web app's queries or
  in Power BI. Shared dimensions filter facts instead. Where a specific pair
  of fact rows needs to be recovered (for example, the fact_absence episode a
  fact_safety_incident row produced), match on the columns both facts already
  carry (Employee_Key + date) at query time rather than storing a fact-to-fact
  foreign key. In Power BI this is the same DAX-measure pattern used for
  fact_vacancy/fact_recruitment below, not a modeled relationship.
- Shared dimensions filter facts with single-direction relationships.
- fact_workforce_snapshot is employee-month grain and includes zero absence
  employees. Use it for denominators and employee trend measures.
- fact_absence is episode grain. Use it for absence-type filtering and
  episode-level analysis. `Duur_dagen` is calendar duration; workday and hour
  fields are preferred for capacity and verzuim metrics.
- Satisfaction is time-varying. `SatisfactionBand_Key` is therefore stored on
  the workforce snapshot, on absence episodes at their start date, and on exit
  events at their departure date.
- Engagement is a separate time-varying score on the workforce snapshot and
  exit events. Voluntary constructive contribution signals feed both its score
  and its dominant driver; satisfaction, relative pay, manager, performance
  and career momentum remain bounded context. Its effects on future performance
  and attrition are deliberately capped.
- Performance excludes absence, overtime and out-of-hours availability. Its
  drivers describe bounded, role-relevant execution, experience, collaboration,
  initiative or knowledge sharing.
- `role_career_paths` is the configuration-owned source for relevant education
  and promotion targets. `dim_role` exposes both lists; promotions use only
  configured targets, while transfers remain separate lateral moves.
- Time to fill is defined for closed vacancies. For hire-source analysis, join
  on the accepted recruitment record's Vacancy_Key at query time (a SQL join
  in the web app, a DAX TREATAS measure in Power BI) rather than a stored
  fact-to-fact relationship.

Operational notes
-----------------
- The HTTP endpoint uses HR_SIMULATION_MODE to select full or incremental
  (any other value is rejected).
- The timer trigger always uses incremental mode.
- Run a full simulation after adding snapshot columns or driver keys; an
  incremental run does not backfill existing snapshot rows.
- Local Azure Functions timer support requires Azurite through
  AzureWebJobsStorage=UseDevelopmentStorage=true.
- A full run is required after historical-logic or reporting-schema changes.
- acquire_simulation_lock retries its initial SQL connection a few times
  (simulation_lock.CONNECT_ATTEMPTS/CONNECT_RETRY_DELAY_SECONDS) to ride out
  a transient Azure SQL connection failure (e.g. an HYT00 login timeout)
  instead of failing the whole run on one blip.
- weekly_hr_run re-raises after logging a failed run, so Azure marks that
  invocation Failed; before this it was swallowed and every timer run showed
  Succeeded even when the pipeline had not written anything.
- The SQL writer manages table creation, additive columns, retired tables,
  primary keys, foreign keys and indexes. There is no retention/deletion
  policy: the demo keeps its full simulated history indefinitely (an earlier
  5-year retention step was removed - see BACKLOG.md AR-01).
